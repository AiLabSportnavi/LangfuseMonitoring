# Full technical and security audit — 2026-08-12

**Scope:** the whole self-hosted observability and prompt-management stack — Langfuse, Grafana,
Prometheus, the data services, the Caddy edge, the Eve agent integration, secrets handling, and the
repository itself.
**Host:** `sportnavi-langfuse.sportnavi.de` / `deploy-ui.sportnavi.de`, both `5.9.95.174` (Hetzner, EU).
**Mode:** read-only. No production change, no destructive action, no account created, no credential used
beyond what already sits in the local working tree.
**Auditor vantage:** egress IP `2.214.240.43` — **which is inside `ADMIN_ALLOWLIST`**. Every claim about
external reachability below was therefore re-verified from an independent, non-allowlisted vantage
(Anthropic's URL fetcher). This distinction is the reason two findings in this report contradict the
existing `docs/SECURITY-REVIEW.md`.

## 1. Executive summary

The platform is **well engineered and unusually well documented**, with a genuinely strong core: no
data service is exposed, secrets are randomly generated and were never committed, TLS is correct,
images are pinned, and the agent-side tracing layer is careful about payloads, masking and failure
isolation. The architectural reasoning captured in `CLAUDE.md` and the pitfalls documents is better
than most production systems ever get.

It is **not production-ready**, for four reasons that are independent of that quality:

| # | Issue | Severity |
|---|---|---|
| F-01 | **The Grafana admin UI is reachable from the open internet.** The `ADMIN_ALLOWLIST` gate that the config, the compose comments and `CLAUDE.md` all claim protects it is not in force on the deployed server. Auth reduces to one local password. | **Critical** |
| F-02 | **Langfuse self-registration may be exposed to the internet.** The sign-up page renders publicly and no signup/org-creator restriction is set in the local config. **Downgraded to Unverified — see the correction notice.** | *Unverified* |
| F-03 | ~~Password login still enabled alongside Entra SSO~~ — **WITHDRAWN, see the correction notice.** | ~~High~~ |
| F-04 | **There are no backups.** Not misconfigured — absent. Postgres holds every project API key, org and user, and `OPERATIONS.md` §6–8 is a specification with nothing implementing it. | **High** |
| F-07 | **The repository's `infra/.env` has drifted from the running server**, now proven concretely. Local config is not evidence about production state. | **Medium-High** |

> ### ⚠️ Correction notice — 2026-08-12, post-publication
>
> **F-03 is WITHDRAWN.** It claimed password login was still enabled. It is not. A live
> `POST /api/auth/callback/credentials` — sent with a deliberately wrong password so that no session
> could be created — returns:
>
> ```
> Sign in with email and password is disabled for this instance. Please use SSO.
> ```
>
> The original finding rested on `/api/auth/providers` listing the `credentials` provider. That is
> **not** evidence of enforcement; it reflects NextAuth's *registered* providers, exactly as
> `DEPLOYMENT-PITFALLS.md` #11 already documents. This report criticised `CLAUDE.md` §12.1 for weak
> evidence on this very control, then made the same error in the opposite direction. The correct
> verification is the CSRF-token POST above, and it is now item B1 in the checklist.
>
> **F-02 is downgraded from High to Unverified.** `POST /api/auth/signup` reaches Zod password
> validation rather than a "disabled" gate — but Langfuse may evaluate the signup flag *after* input
> validation, so this is inconclusive in both directions. Settling it requires reading the running
> container's environment or creating an account; neither was in scope.
>
> **Root cause of both errors:** the report treated `infra/.env` as describing the server. It does
> not. The local file says `AUTH_DISABLE_USERNAME_PASSWORD=false`; the server enforces `true`.
> **Every finding below that cites `infra/.env` alone must be re-checked against the running
> container before it is acted on** — specifically F-02 and the `ADMIN_ALLOWLIST` contents in F-05.
> F-01 is unaffected: it was established from external HTTP behaviour, never from config.

Cutting across all four is a **meta-finding (F-06)**: the repository's own test suite passes on all six
config checks, including one that explicitly asserts *"grafana site block is allowlist-gated with a
default deny"* — while the deployed surface is open. The tests assert the presence of text in a config
file, not the behaviour of the running system. This is the same failure mode already recorded once in
this repo (the `rate_limit` false-pass, `SECURITY-REVIEW.md` P4), recurring in a new place. Green tests
here are currently evidence of intent, not of state.

**Readiness assessment: 5.5 / 10.** Suitable for internal, non-sensitive telemetry today. Not suitable
for production agent traffic, multi-project onboarding, or anything with a data-loss or
confidentiality consequence until F-01 through F-04 are closed.

## 4. Langfuse audit

### Verified working

- `GET /api/public/health` → `200 {"status":"OK","version":"4.6.0"}`
- `GET /api/public/ready` → `200`
- `GET /api/public/v2/prompts` without a key → `401 {"message":"No authorization header"}` — **verified
  from an external non-allowlisted client**, so the REST API is key-authenticated, not IP-gated. This
  is the documented intent and it holds.
- HTTP→HTTPS `308` redirect; TLS 1.2/1.3 only, TLS 1.0/1.1 refused; ZeroSSL ECC DV cert valid
  2026-08-10 → 2026-11-08.
- Headers: HSTS 1y + `includeSubDomains`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex`, `Server` stripped.
- Entra SSO provider registered: `/api/auth/providers` lists `azure-ad`.
- Ingest path is correct (`/api/public/otel/v1/traces`); the canary reads back via
  `/api/public/v2/observations`, correctly accounting for `events_only` mode.

### Problems

**F-02 · Self-registration exposed to the internet · HIGH**

`https://sportnavi-langfuse.sportnavi.de/auth/sign-up` renders the Langfuse SPA to an arbitrary
internet client (verified externally — it returned the app shell, *not* Caddy's `403 Not authorized`).
`AUTH_DISABLE_SIGNUP` is absent from `infra/.env` and from `compose.yaml`, and
`LANGFUSE_ALLOWED_ORGANIZATION_CREATORS` is absent too.

*Why it matters:* until the `ADMIN_ALLOWLIST` was removed from the Langfuse vhost, network position was
the control preventing this. That control is now gone and nothing replaced it. Any internet user can
create an account on your instance and, absent an org-creator restriction, create an organisation and
project inside it — consuming ClickHouse and NVMe capacity on the box whose primary documented risk is
disk exhaustion (`CLAUDE.md` §10.1), and establishing an authenticated foothold for any future
privilege-escalation bug in the app.

*Limiting factor, stated honestly:* a freshly self-registered user has **no membership in your existing
org**, so this is not direct exposure of your trace data. That is why this is High and not Critical.
**I did not create an account to prove the end-to-end path** — that would be a production mutation.
The reachability of the page and the absence of both env vars are verified; the exact post-registration
capability is *not verified* and is listed in §21.

*Remediation:* the correct control is **not** `AUTH_DISABLE_SIGNUP=true` — per Langfuse docs it also
blocks invited colleagues who have no account yet, which breaks onboarding. Use the identity boundary
instead:
1. Set `AUTH_DISABLE_USERNAME_PASSWORD=true` (see F-03) so the only registration path is Entra, and the
   single-tenant app registration becomes the domain restriction.
2. Set `LANGFUSE_ALLOWED_ORGANIZATION_CREATORS` to the explicit admin address list so a new identity
   cannot mint an org.

**F-03 · Password login still enabled, bypassing the SSO tenant lock · HIGH**

`AUTH_DISABLE_USERNAME_PASSWORD=false` in `infra/.env`, and `/api/auth/providers` confirms live that the
`credentials` provider is registered alongside `azure-ad`.

*Why it matters:* the entire security argument for the SSO migration is that the app registration is
single-tenant, so Entra is authoritative for who gets in. A live password provider sits beside that
lock and does not respect it. Layered on top:
`LANGFUSE_INIT_USER_EMAIL=platform@example.com` with a 64-hex `LANGFUSE_INIT_USER_PASSWORD` is still
populated, and `compose.yaml`'s own comment states these **re-create the org and seed user on every web
start** — so this password account cannot be removed through the UI. It comes back on the next restart.

*Correction to an existing claim.* `CLAUDE.md` §12.1 records as evidence that "password login is
genuinely refused (`POST /api/auth/callback/credentials` → redirect to `signin?csrf=true`)". That
inference is wrong: `csrf=true` is Auth.js's **missing-CSRF-token** response. It is what you get for
posting without first fetching a CSRF token, regardless of whether the provider is enabled. It is not
evidence of refusal, and the providers endpoint contradicts it.

*Remediation:* confirm an Entra identity holds OWNER on the org (via the UI, by signing in), **then**
blank the five `LANGFUSE_INIT_USER_*` variables and set `AUTH_DISABLE_USERNAME_PASSWORD=true`. Order
matters — reversing it leaves the platform with no reachable administrator.

**F-17 · Prefix-glob route matchers · LOW** — `path /api/public/otel* /api/public/ingestion*` also
matches `/api/public/otelXYZ` and any future sibling path under that prefix, which would inherit the
public, key-only treatment without review. Carried over unremediated from `SECURITY-REVIEW.md` P8.

## 5. Grafana audit

**F-01 · Grafana admin UI is reachable from the open internet · CRITICAL**

This is the headline finding, and it directly contradicts `infra/compose.monitoring.yaml`
("Grafana is reached through the grafana.<domain> site block in the Caddyfile, gated by
ADMIN_ALLOWLIST"), `CLAUDE.md` §12.1, and the repo's own passing test.

**Evidence, from an external non-allowlisted client:**

```
GET https://deploy-ui.sportnavi.de/api/health
→ {"database": "ok", "version": "13.0.6", "commit": "10dd6600174a4fbd9135f2e90aa784f58afe4f64"}

GET https://deploy-ui.sportnavi.de/login
→ Grafana's own application page ("If you're seeing this Grafana has failed to load its
   application files ...") — i.e. the request was PROXIED TO GRAFANA
```

Caddy's deny handler returns the literal body `Not authorized`. Neither response is that. The request
reached `grafana:3000`. `deploy-ui.sportnavi.de` resolves to `5.9.95.174`, the same box, and
`https://deploy-ui.sportnavi.de/api/public/health` returns Grafana's `auth.unauthorized` JSON —
confirming that vhost proxies to Grafana and not to Langfuse.

**Compounding factors:**
- **Grafana SSO is off.** `GRAFANA_SSO_ENABLED` is absent from `infra/.env`, so it defaults to `false`.
  Authentication is therefore a *single local admin account*: user `admin`, password from
  `GRAFANA_ADMIN_PASSWORD`. No MFA, no lockout, no second factor.
- The password itself is fine — 64 hex characters from `generate-secrets.sh`. **That single random
  string is currently the only thing between the internet and your monitoring plane.**
- The `/login*` rate limiter in the Caddyfile is nested *inside* the `handle @trusted` block. If the
  deployed config lacks that gate, it plausibly lacks the limiter too, leaving the login form with no
  brute-force protection. *Not verified* — proving it requires flooding production, which I did not do.
- Grafana holds the datasource to Prometheus, which is otherwise deliberately un-ingressed. Grafana
  access is therefore transitive read access to every metric on the box.

**Root cause — narrowed, not closed.** I eliminated the most likely benign explanation. Hypothesis:
`ADMIN_ALLOWLIST` never reaches the container (the exact failure recorded in `DEPLOYMENT-PITFALLS.md`
#14), leaving an empty matcher that admits everyone. I tested this directly by running
`caddy:2.11.4-alpine` locally against a minimal reproduction of the matcher:

```
ADMIN_ALLOWLIST=""              → adapts to  "match":[{"remote_ip":{}}]   → runtime: "Not authorized"
ADMIN_ALLOWLIST="10.99.99.0/24" → runtime: "Not authorized"
ADMIN_ALLOWLIST="<the 5 CIDRs>" → adapts to all five ranges correctly
```

An empty allowlist **fails closed**. So the open surface is *not* caused by a missing variable. The two
remaining candidates are (a) the deployed `Caddyfile` differs from this repo's copy and its Grafana
block has no `@trusted` gate — `CLAUDE.md` §12.1 explicitly warns the repo "may still lag the deployed
server" — or (b) `ADMIN_ALLOWLIST` on the server contains a broad range such as `0.0.0.0/0`.

**One command on the host settles it:**
```bash
docker exec langfuse-caddy-1 sh -c 'echo "$ADMIN_ALLOWLIST"; cat /etc/caddy/Caddyfile' | sed -n '/GRAFANA/,$p'
```

**Remediation, in order:**
1. Restore the `@trusted` gate on the Grafana vhost *or* correct `ADMIN_ALLOWLIST`, then re-verify from
   an off-network client — not from your own machine, which is allowlisted.
2. Enable Grafana Entra SSO (`GRAFANA_SSO_ENABLED=true`, `GRAFANA_AZURE_AD_*`, tenant pinned via
   `GF_AUTH_AZUREAD_ALLOWED_ORGANIZATIONS`). The scaffolding is already written and inert —
   this is a `.env` change plus an app registration.
3. Only after a successful Entra sign-in, set `GRAFANA_SSO_ROLE_STRICT=true`. Keep the local admin as
   break-glass; do **not** set `GRAFANA_DISABLE_LOGIN_FORM=true` until SSO is proven by signing in.

**F-15 · Duplicate, conflicting `X-Frame-Options` on Grafana · LOW** — verified live:

```
X-Frame-Options: SAMEORIGIN   ← Caddy
X-Frame-Options: deny         ← Grafana
```

Caddy's `header X-Frame-Options "SAMEORIGIN"` **appended** rather than replaced. Browsers treat
duplicate/conflicting `X-Frame-Options` as invalid and several ignore the header entirely, so the
clickjacking protection the Caddyfile comment intends may be absent in practice. Fix with the
replacement operator: `header >X-Frame-Options "SAMEORIGIN"`, or set
`GF_SECURITY_X_FRAME_OPTIONS` and drop Caddy's copy so exactly one source owns it.

### Verified good on the monitoring stack

Prometheus has **no ingress at all** — verified by port probe (9090 filtered from outside) and by
`compose.monitoring.yaml` publishing no host port. Dashboards and the datasource are provisioned as
code, `editable: false`. Anonymous access, sign-up and org-create are all explicitly disabled.
Grafana's analytics/update callbacks are off (GDPR-appropriate). No credential is embedded in any
dashboard JSON (searched). `GF_SECURITY_ADMIN_PASSWORD` uses `:?` so an unset value fails the command
instead of silently defaulting to `admin` — a genuinely good detail.

## 7. Agent / integration audit

**Verified good.** The instrumentation layer is careful in ways that matter:

- **Client-side masking** (`secretRedactionMask`) applied at export, covering `Bearer`/`Basic` headers,
  Langfuse `pk-/sk-` keys, OpenAI-shaped keys, AWS `AKIA…`, `api_key=`/`password=` assignments, plus
  wholesale redaction of `authorization|token|secret|password|api_key` object keys, with a depth guard
  against cyclic payloads. Correctly chosen as *client-side* — server-side masking is EE **and** writes
  the unmasked event to blob storage first.
- **No SSRF surface.** Both tools (`get_weather`, `get_forecast`) are offline table lookups. Nothing in
  the agent fetches a user-controlled URL. Model and Langfuse endpoints come from environment variables
  only.
- **Prompt injection is explicitly tested**, not assumed: `datasets/.../03-prompt-injection.json` covers
  system-prompt exfiltration, persona override, injection smuggled through a *tool argument*, and
  forged tool output — with behavioural assertions (did it still call the tool?) rather than prose
  matching. `agent/instructions.md` carries matching boundary rules. This is better than most
  production agents.
- **Payload discipline** — runtime context is kept deliberately small to avoid the quadratic
  message-history growth `CLAUDE.md` §7.5 warns about; step payloads are stored once by the enricher.
- Sampling knob shipped at 100% with per-trace caching so partial traces cannot occur.
- `npm audit`: **0 vulnerabilities** across 126 resolved dependencies.

**F-11 · Channel auth is a placeholder · MEDIUM**

`agent/channels/eve.ts` ships `vercelOidc()` + `localDev()` + `placeholderAuth()`. For a PoC that is
correct and self-documenting. Two consequences to be deliberate about:

1. This file is the template every future project will copy. Copied as-is into a real project, it
   deploys an agent whose browser-facing channel has no application auth provider.
2. `langfuse.user.id` falls back to a synthesised principal (`local-dev` / anonymous), so **per-user

*Remediation:* before any real project onboards, replace `placeholderAuth()` with the real provider and
make that substitution a required step in `RUNBOOK-onboarding.md`.

**Data-separation note:** trace isolation between projects rests entirely on per-project API key pairs
and Langfuse's own project scoping. That model is sound, and `provision-project.sh` correctly refuses
to silently mint a second key pair for an already-provisioned project. Its output prints the secret key
to stdout — necessary for handover, but it means the key lands in terminal scrollback and would land in
CI logs if ever run non-interactively. Treat that script as interactive-only.

## 8. Infrastructure and Docker audit

**Verified good:** only Caddy publishes host ports (`80`, `443`) — asserted by
`test-monitoring-config.sh` and confirmed by external port probe. All images pinned to explicit
versions, never `latest`, with a written rationale. `compose.local.yaml` and `compose.monitoring.yaml`

**F-09 · cAdvisor runs `privileged: true` · MEDIUM**

`compose.monitoring.yaml` grants cAdvisor `privileged: true` with `/`, `/var/run`, `/sys`,
`/var/lib/docker` and `/dev/disk` mounted plus `/dev/kmsg`. This is effectively root on the host. The
file documents and accepts this, and the mounts are read-only — but `/var/run` includes the Docker
socket path, and a privileged container on the same bridge network as everything else is the largest
single blast radius in the stack. It is the right call to flag it as the first thing to revisit at
Tier 2 (where kubelet supplies these metrics instead); until then, note that any cAdvisor CVE is a
host-compromise CVE here.

*Mitigation available now:* drop `privileged: true` and grant only what is needed
(`cap_add: [SYS_PTRACE]`, `security_opt: [apparmor:unconfined]`, `devices: [/dev/kmsg]`), then verify
the container/OOM panels still populate. Test before adopting — cAdvisor's requirements vary by kernel.

**Other observations**

- No container sets `read_only: true`, `no-new-privileges`, or non-root `user:`. Defence-in-depth
  hardening that costs little and is currently absent across the board. *(Low)*
- No `deploy.resources.limits` anywhere: a runaway container can starve the box, including starving
  ClickHouse, which is the component whose saturation the whole monitoring design exists to catch.
  *(Low-Medium)*
- Both Docker networks are flat: Grafana, Prometheus and every exporter share one bridge with Postgres,
  ClickHouse and Valkey. A compromise of any exporter has direct network reach to every datastore.
  Splitting `monitoring` and `data` networks would be a cheap improvement. *(Low-Medium)*

## 13. Logging and tracing audit

**Verified good.** Caddy writes rolled JSON access logs (100 MiB × 14 for Langfuse, 50 MiB × 7 for
Grafana) with no request bodies — enough for per-project ingestion attribution, no payload leakage.
Span export is high-signal by default: Langfuse's GenAI filter plus an explicit `ai.eve.turn` exception
to fix a real multi-root bug, with `LANGFUSE_EXPORT_ALL_SPANS=1` as an escape hatch. The
`SpanAttributeDebugProcessor` prints values rather than just keys — a deliberate fix for a case where a
present-but-`false` attribute looked identical to a present-and-`true` one. Errors are always kept
regardless of sampling.

Two honest limitations already documented in-repo and confirmed here: the sampler is streaming, not
buffering, so an error arriving after a sibling was already dropped cannot rescue that sibling (no
effect at the default rate of 1); and Langfuse exposes **no Prometheus endpoint**, so worker queue
depth is derived from BullMQ's Redis keys — a wrong `REDIS_QUEUE_KEY_PATTERNS` yields empty panels that
read as a healthy queue rather than an error. `discover-queue-keys.sh` exists to prevent that and the
current value is non-default (68 chars), suggesting it was actually run.

**No finding.** This area is in better shape than most of the stack.
